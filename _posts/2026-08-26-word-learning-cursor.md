JYP-Word는 사용자가 하루에 영어 단어 20개씩 학습하는 서비스다. 처음에는 "사용자가 학습한 단어를 전부 저장하면 되지 않을까?"라고 생각했다. 하지만 학습 기록이 쌓이는 상황을 따라가 보니, **무엇을 저장할지보다 얼마나 적은 정보로 학습 상태를 표현할 수 있는지가 더 중요한 문제**였다.

> **한 줄 요약**  
> 학습한 단어 ID 목록을 계속 쌓는 대신, 시작 위치와 현재 위치를 나타내는 커서만 저장하도록 설계를 바꾸었다.
{: .prompt-info }

## 처음 생각: 학습한 단어를 모두 저장하자

가장 단순한 방법은 사용자가 학습한 단어와 학습 내용을 DB에 하나씩 저장하는 것이다. 예를 들어 사용자가 오늘 20개 단어를 학습하면, 해당 20개의 단어 ID를 학습 이력으로 남기는 방식이다.

하지만 사용자가 늘고 학습이 누적되면 기록도 계속 증가한다. 하루 20개라는 양은 한 명에게는 작지만, 서비스 전체로 보면 `하루 학습량 × 사용자 수`만큼 데이터가 쌓인다. 당시에는 회원 기능도 없었기 때문에, 모든 사용자의 학습 상태를 서버 DB에서 관리하는 구조가 아직은 과하다고 느꼈다.

## IndexedDB로 학습 상태를 사용자 브라우저에 저장

초기 버전에서는 로그인 없이도 학습 진행 상황을 유지하는 것이 목표였다. 그래서 서버 DB 대신 브라우저의 **IndexedDB**에 학습 데이터를 저장하기로 했다.

처음 계획은 간단했다.

1. 사용자가 학습한 단어 목록을 IndexedDB에 저장한다.
2. 다음 학습 때 저장된 목록을 읽는다.
3. 이미 학습한 단어는 제외하고 새로운 단어 20개를 제공한다.

이 방식은 구현하기 쉽고 회원 기능이 없는 서비스에도 잘 맞는다. 다만 시간이 지날수록 다른 문제가 생겼다.

## 문제: 학습 이력이 많아질수록 필터링도 커진다

사용자가 학습을 계속하면 IndexedDB 안의 "이미 학습한 단어" 목록도 계속 길어진다. 다음 단어를 추천할 때마다 전체 단어 데이터에서 학습 이력을 확인하고 제외해야 한다.

처음에는 20개 단어만 처리하므로 문제가 없어 보인다. 그러나 데이터셋이 커지고 학습 기간이 길어지면, 매번 학습 이력과 비교해 미학습 단어를 찾는 구조는 점점 불필요하게 복잡해진다.

결국 질문을 바꾸게 되었다.

> "학습한 모든 단어를 기억해야 할까?"  
> 아니면 "사용자가 어디까지 학습했는지만 알면 될까?"
{: .prompt-tip }

## 해결: 단어 목록이 아닌 커서를 저장하자

학습용 데이터셋의 각 단어에 순서 번호를 부여하고, 사용자의 학습 위치를 **커서(cursor)** 로 관리하기로 했다.

처음 접속한 사용자에게 임의의 시작 커서를 발급한다. 이후에는 해당 위치부터 하루에 20개씩 단어를 제공하고, 학습이 끝날 때마다 현재 커서를 20만큼 이동한다.

```text
데이터셋:  [0] [1] [2] ... [117] [118] ... [136] [137] ...
                              ↑                    ↑
                        current_cursor       다음 학습 시작점

오늘 제공: 118번 ~ 137번 단어, 총 20개
```

이제 저장해야 할 핵심 정보는 "어떤 단어들을 학습했는가"가 아니라 "어디에서 시작했고, 지금 어디까지 왔는가"가 된다.

| 저장 값 | 역할 |
| --- | --- |
| `dataset_id` | 사용할 셔플 데이터셋 식별 |
| `start_cursor` | 이번 회독을 시작한 위치 |
| `current_cursor` | 다음 학습을 시작할 현재 위치 |

회원 기능이 없는 현재 구조에서는 이 값들을 IndexedDB에 저장한다. 추후 회원 기능을 추가하더라도, 단어별 학습 이력 전체가 아니라 이처럼 작은 진행 상태만 서버에 동기화하는 방향을 고려할 수 있다.

## `start_cursor`와 `current_cursor`가 필요한 이유

`current_cursor` 하나만 저장하면 현재 위치는 알 수 있다. 하지만 사용자가 처음 시작한 위치를 모르면 데이터셋을 한 바퀴 모두 학습했는지 판단하기 어렵다.

그래서 두 값을 함께 저장한다.

- `start_cursor`: 사용자가 이번 학습 사이클을 시작한 위치
- `current_cursor`: 현재 학습이 진행된 위치

현재 커서가 데이터셋 끝을 넘어가면 처음으로 돌아오도록 처리한다. 이때 `current_cursor`가 다시 `start_cursor`에 도달하면 한 번의 회독을 완료했다고 판단할 수 있다.

```text
시작: start_cursor = 118, current_cursor = 118
학습: current_cursor = 138 → 158 → ...
완료: 데이터셋을 순환해 current_cursor가 다시 118에 도달
```

## 랜덤성은 셔플 데이터셋과 랜덤 커서로 보완

커서 방식은 효율적이지만, 하나의 고정된 데이터셋만 사용하면 사용자는 결국 정해진 순서로 단어를 보게 된다. 시작 위치만 무작위여도, 이후 순서는 동일하다.

이를 보완하기 위해 원본 단어 데이터를 여러 번 셔플한 **N개의 데이터셋**을 만들어 두기로 했다. 사용자가 처음 접속할 때는 다음 두 값을 무작위로 선택한다.

1. 셔플된 데이터셋 하나
2. 해당 데이터셋 안의 시작 커서 하나

```text
원본 데이터셋
     ├─ 셔플 데이터셋 A + 랜덤 커서
     ├─ 셔플 데이터셋 B + 랜덤 커서
     └─ 셔플 데이터셋 C + 랜덤 커서
```

이 구조라면 커서 방식의 단순함을 유지하면서도, 사용자마다 다른 단어 순서와 시작점을 제공할 수 있다.

## 회고

처음에는 학습 기록을 많이 남기는 것이 정확한 관리 방법이라고 생각했다. 하지만 이 기능에서 정말 필요한 것은 단어별 상세 이력이 아니라, 사용자가 학습을 어디까지 진행했는지를 나타내는 상태값이었다.

이번 설계를 통해 모든 정보를 저장하는 것보다, 문제에 필요한 최소한의 상태만 저장하는 편이 더 단순하고 확장성 있는 구조가 될 수 있다는 점을 배웠다. 앞으로 회원 기능과 복습 기능을 추가하게 되면 학습 이력을 더 세밀하게 관리해야 할 수 있다. 그때도 단순히 데이터를 쌓기보다, 어떤 기능을 위해 어떤 상태가 필요한지부터 다시 고민해 보고 싶다.
